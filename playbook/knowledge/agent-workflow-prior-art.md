# Agent Workflow Prior Art

Reviewed 2026-10-02. This note consolidates the supplied video summaries and the linked first-party material into mechanisms that can inform Workbench. A supplied summary is evidence of what the summary says, not a verified transcript. Product details and benchmark claims below are attributed to their sources.

## 1. Pi and the local engineering loop

The [Ronacher interview](https://www.youtube.com/watch?v=SxuQs9GGYbk) describes a compact agent loop: run locally in the real repository, use standard shell and Git tools for investigation, keep dependencies and tests available, inspect changes as a human, and offload only bounded work. [Pi's own documentation](https://pi.dev/docs/latest/cli) confirms that its default model-facing tools are `read`, `bash`, `edit`, and `write`; [extensions](https://pi.dev/docs/latest/extensions) add capability without making every workflow part of the core. Pi was created by Mario Zechner and later acquired by Earendil, whose founders include Armin Ronacher. The supplied interview summary incorrectly calls Ronacher Pi's creator. [Earendil's announcement](https://earendil.com/posts/announcing-pi-and-lefos/).

Workbench already follows most of this pattern. Pi runs in a repository with Git, `rg`, a small tool set, native sessions, and explicit verification. `AGENTS.md` carries durable project rules, while optional skills carry repeatable workflows. Workbench adds a permission policy, safe Git gates, one worktree-isolated worker, read-only connectors, a thin browser wrapper, and terminal context indicators. The host layer owns Tailscale and mobile continuity through Paseo. These additions mostly preserve the small core, but every extension increases process trust: it executes with Pi's operating-system permissions. The [current inventory](../../docs/pi-capabilities.md) and [build philosophy](../../docs/pi-build-philosophy.md) document that residual risk.

The important distinction is **composability versus authority**. Shell pipelines are efficient for searching and transforming trusted local files. They are a poor substitute for a connector that hides credentials, applies source authorization, or validates a consequential write. Pi's model-level permission extension is a useful tripwire, not an operating-system sandbox. Use the restricted launch or a sandboxed harness for untrusted execution; keep external page retrieval on dedicated read-only tools. Do not add an unrestricted `curl` fallback merely because a web read failed.

The interview predates a relevant change: [Pi Durable](https://earendil.com/posts/pi-durable/) was announced on 2026-10-01 as an experimental package for crash-resumable conversations, task checkpoints, multiple clients, and replaceable execution environments. It is separate from the terminal coding agent. Its safe-versus-unsafe tool replay distinction is a strong reference for external writes, but it does not make an interrupted third-party side effect exactly once. Workbench has no demonstrated need to install it into the daily coding loop. Consider it for a real long-lived agent application only after evaluating storage, recovery, authority, and operating cost against the application's existing durable-workflow options.

The installed `pi --version` in this workspace reported `0.85.1` on 2026-10-02, while Workbench's tutorial documents a `0.86.1` configuration snapshot and upstream has announced Pi 1.0. Treat the live version and deployment state as a separate reconciliation task before relying on a new upstream feature. No upgrade was made for this research.

## 2. Verification and production feedback

| Prior art | Mechanism worth retaining | Limit or adoption test |
| --- | --- | --- |
| [Anthropic verification loops](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills) and the [supplied video](https://www.youtube.com/watch?v=mQZB0l-rhxE) | Turn a repeated manual visual or functional check into a runnable project verification procedure with explicit observations and pass criteria | The skill is a repeatable procedure, not evidence by itself. Confirm the actual browser or application state after each change. |
| [GitHub's Copilot runtime migration to Rust](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/) | Migrate in small reviewable slices, preserve the old contract until a slice is verified, run end-to-end checks, and watch real releases | Pull-request and line counts measure throughput. Tests can encode a mistaken contract, so inspect production symptoms and recovery paths. |
| [Cursor Rollouts](https://cursor.com/changelog/rollouts-and-security-reviewer) | Derive a monitoring plan from the proposed change before deploy, then compare real production behavior and alert or propose a revert | Cursor says it may open a revert pull request or request an agent fix; it does not merge or roll back by itself. Use application metrics and operator-owned gates. |
| [Kiro's software factory](https://kiro.dev/blog/software-factory-1000-prs/) | Persist task state, coordinate bounded work, control permissions, and retain an inspectable review queue | Its 1,000 merged pull requests in a week is a first-party throughput claim without a quality or rework denominator. Do not build a factory without measured recurring demand. |
| [Stateless MCP specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/) and [AWS deployment guidance](https://aws.amazon.com/blogs/architecture/mcp-went-stateless-is-your-aws-mcp-server-deployment-well-architected/) | Remove transport affinity where useful; keep workflow state and identity explicit in the application | Stateless transport does not make a business operation idempotent or eliminate ambiguous write outcomes. |
| [Cloudflare's EmDash migration](https://blog.cloudflare.com/cloudflare-blog-uses-emdash/) | Move real traffic gradually with a fallback and measured results | A successful platform migration pattern does not by itself justify adopting EmDash. |
| [Signadot's sandbox routing](https://www.signadot.com/docs/concepts/sandbox) and the [linked distributed-verification analysis](https://thenewstack.io/agentic-verification-distributed-systems/) | Route a test request through only the changed service while the rest of a distributed stack uses a stable baseline | Requires propagated environment identity and isolation of writable state. Relevant when a full local stack is too slow and shared staging causes cross-test interference, not for ordinary single-service work. The linked analysis could not be read directly; Signadot's documentation supports the mechanism. |

The shared verification loop is: record the proposed change and expected outcome; run deterministic checks and representative human-interface checks; observe the deployed effect when applicable; compare with the predeclared expectation; stop or recover on mismatch. This is more useful than merely asking an agent to review its own output. For a small application, a CLI that starts the real app and returns structured state may close the loop. For a distributed system, complete per-agent copies can be slow and expensive, while shared staging can make parallel checks contaminate one another. Signadot's request routing is one documented approach to isolate each changed service against a stable shared stack; queues, databases, and external effects still need their own isolation. The [harness operations article](https://www.infoq.com/articles/agent-harness-build-one/) adds evaluation, observability, and cost as runtime responsibilities, not just model prompting.

Kiro describes five stages of growing concurrency: one interactive session; several tabs coordinated by a human; remembered and scheduled work; a queued agent pipeline; and a coordinator that manages the sessions. Each stage addresses a real bottleneck created by the prior stage. The useful lesson is to measure where work waits before adding another coordinator. The published 1,000-PR week still needs denominators for accepted changes, reversions, incidents, and human review time. Workbench currently has one bounded worktree worker and a parent verifier. It should keep that ceiling until repeated work shows coordination, rather than implementation, is the limiting factor.

GitHub's migration and Cursor's Rollouts cover different verification windows. GitHub kept migration changes small enough for tests, review, and repeated production releases to reveal wrong contracts and state assumptions. Rollouts asks what signals would prove a particular change healthy before it deploys, then checks those signals per environment. Together they suggest a practical release record for consequential changes: expected behavior, affected contract, test result, deployment identity, monitoring signals, observed effect, and recovery action. The record should be concise and attached to the change; a generated risk essay with no observable signal adds little value.

## 3. Decisions, security, and business actions

[Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev) and [GLiClass](https://github.com/Knowledgator/GLiClass) address fast classification or typed decisions. [Vercel's form-router example](https://vercel.com/kb/guide/jev-ai-sdk-form-router) demonstrates a classifier with a fallback. These can help route a request, but a high confidence score cannot authorize a write or establish source truth. Compare on calibrated accuracy, abstention, latency, total cost, and downstream errors. No evidence reviewed here supports the accusation that Jev copied GLiClass.

[OpenAPPA](https://github.com/archestra-ai/OpenAPPA) is different: it proposes information-flow policy around agent actions. [Meta Muse's published architecture](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse) similarly separates the acting agent from credentials and permission authority. The mechanism to borrow is an enforcement point outside the model, with narrow credentials, action-level scope, and an audit of what actually happened. Vendor or author attack results do not establish complete coverage. The [agent control-plane comparison](agent-control-plane-landscape.md) tracks Muse alongside Grok Bot and Dots; the [direct-integration boundary](agent-capability-patterns.md#19-direct-agent-integrations-and-application-owned-boundaries) applies this lesson to enterprise software.

## 4. The twelve Opus 5.5 tips, tested against this setup

The [supplied RoboNuggets video summary](https://www.youtube.com/watch?v=vsGwx28z4jk) mixes durable practices with model- and promotion-specific advice. The available source is the supplied summary, not a full verified transcript.

| Tips | Workbench disposition |
| --- | --- |
| 1–2: medium effort and compare levels | **Use conditionally.** [Anthropic documents](https://platform.claude.com/docs/en/build-with-claude/effort) medium as the Opus 5.5 default and recommends evaluating effort on real tasks. Keep Workbench's explicit model and thinking controls; compare quality and latency before changing a default. |
| 3: one `AGENTS.md` | **Already adopted.** It is the canonical shared instruction file; project rules stay with their projects. |
| 4: change effort without losing cache | **Model and API specific.** Anthropic says per-message effort changes preserve cache on supported models; changing top-level effort can invalidate it. Do not assume every client or provider uses the supported per-message path. |
| 5: bank a promotional usage reset | **Do not encode as doctrine.** This depends on an account-specific offer and expiry. |
| 6: do not demand hidden reasoning | **Sound prompt hygiene.** Ask for conclusions, assumptions, and verifiable evidence rather than private reasoning traces. |
| 7: mark all prior answers settled | **Do not add globally.** Workbench preserves open user requests across turns; only explicitly accepted decisions should be treated as settled. |
| 8: checklist for long work | **Use when coordination benefits.** An internal plan or ledger helps multipart tasks, but compulsory visible checklists add ceremony to simple edits. |
| 9–10: time budgets and “time matters” | **Task-level cue only.** A clear deadline can narrow scope, but the phrase is not a dependable execution control or permission to skip required verification. |
| 11: specific visual direction | **Already supported.** Project design systems and concrete examples beat a generic request to “make it nice.” |
| 12: crop dense visuals | **Use as needed.** Inspect relevant regions at useful resolution; do not install an image-processing stack for ordinary screenshots. |

## 5. Persistent assistants and local analytical tools

[Lefos](https://earendil.com/posts/announcing-pi-and-lefos/) is Earendil's public-alpha email-first assistant. The first-party announcement supports collaborative correspondence and an email interface. The supplied summary's Telegram, document-generation, and integration inventory were not verified from that source. Its prior-art value is communication through an open, durable channel and trust earned through bounded collaboration. It is a product to watch, not a reason to add another coding harness or grant an assistant inbox authority today.

The [supplied AI Explained video summary](https://www.youtube.com/watch?v=R9momwXV9w4) raises frontier-model evaluation, automated AI research, and safety-governance questions. [Anthropic's Opus 5.5 release](https://www.anthropic.com/claude-opus-5-5) and [system-card index](https://www.anthropic.com/system-cards) are primary references for those claims. The video's specific internal-benchmark percentage and proposed industry scenarios need direct source verification before becoming Workbench facts. The durable monitoring question is whether released models, evaluations, and containment evidence support a specific longer or more autonomous workflow; a headline benchmark alone does not.

[DuckDB](https://duckdb.org/) is already a Workbench [analytics default](../stacks/data-stores.md), so the [supplied first-impressions video](https://www.youtube.com/watch?v=KJao6oq9MKM) creates no new adoption decision. Its embedded, columnar, file-querying design is useful for local analytical reads; keep a transactional database or source system responsible for concurrent application writes. Avoid adding DuckDB again to the unadopted tool watchlist.
