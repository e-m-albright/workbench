# Product interfaces

Compare component systems, content tools, and application surfaces. Use [design tools](design-tools.md) for visual exploration before implementation.

## Web / Frontend

### Component systems and primitives

Reviewed 2026-10-15 from the official documentation linked below. The existing
Svelte stack already selects **shadcn-svelte plus Bits UI**; recording alternatives
does not change that default. Headless primitives supply interaction behavior
without visual styling. Styled components and larger page blocks sit above them.

| Candidate | Useful role and framework fit | Posture and revisit trigger |

| [shadcn/ui](https://ui.shadcn.com/docs) and [shadcn-svelte](https://www.shadcn-svelte.com/docs) | Component source copied into the application so its visual layer can be customized. The original is React-oriented; shadcn-svelte is a separate, unofficial community port built with Bits UI and Tailwind CSS. | **KEEP the Svelte selection.** Use the original as a React option and design reference, not a directly interchangeable Svelte package. Review copied-code changes and upstream fixes; source ownership also means maintenance ownership. |
| [Shadcn Space / shadcnspace](https://shadcnspace.com/) | Larger dashboard, marketing, and application blocks, components, and templates for React/Next.js; supports Base UI and Radix variants, with free and Pro offerings. | **WATCH AS A DESIGN REFERENCE; evaluate for a real React surface.** No native Svelte offering was established by the reviewed page. Do not combine several primitive libraries for novelty. Trial one difficult
control, such as a dialog containing a combobox, against keyboard navigation,
focus restoration, mobile interaction, server rendering/hydration, and visual
tokens before adding another dependency. Exact licenses, release histories, and
security advisories remain adoption-review work; no packages were installed.

### Geographic maps and choropleths

Reviewed 2026-10-15. **[Svelte MapLibre GL](https://svelte-maplibre-gl.mierune.dev/)**
(`svelte-maplibre-gl`) is a declarative Svelte 5 wrapper around MapLibre GL JS.
It supplies reactive map, marker, source, layer, and interaction integration;
the [quickstart](https://svelte-maplibre-gl.mierune.dev/docs/quickstart) documents
SvelteKit usage and the Vite worker adapter needed for MapLibre GL JS 6.
Do not conflate it with the distinct `svelte-maplibre` wrapper.

**WATCH; strong owner interest, especially for choropleth maps.** A choropleth
colors geographic areas by a value such as a rate or density. MapLibre's
[population-density example](https://maplibre.org/maplibre-gl-js/docs/examples/visualize-population-density/)
shows polygon sources and data-driven fill expressions. The renderer does not
supply the boundary dataset, join keys, metric definitions, basemap hosting,
geocoding, or appropriate statistical interpretation.

Evaluate when a real geographic question needs interactive region shading,
filters, hover detail, and linked tables. Start with synthetic or public regional
data, stable geography identifiers, a visible legend, explicit missing-data
styling, meaningful denominators, and a non-map table alternative. Test large
polygon performance, browser/WebGL support, keyboard alternatives, SvelteKit
hydration, and cleanup. Review tile, font, style, and geocoding providers'
licenses, attribution, costs, and network requests separately from the wrapper.
For sensitive populations, define minimum aggregation and suppression rules;
colored regions and client-side data are not inherently anonymous. No local
map trial, license audit, or performance benchmark has been performed.

### Design-system and UI verification (reviewed 2026-09-24)

- **[shadcn/lint](https://github.com/shadcn-ui/lint)** — **EVALUATE for a Tailwind v4 project with recurring agent-caused design-system drift; do not add globally.** Version 0.2.0 is an MIT ESLint/Oxlint plugin with six deterministic rules for component restyling, raw colors, arbitrary values, inline styles, unknown classes, and dynamic classes. Its useful distinction is actionable diagnostics built from the project's components, variants, and theme. The [primary documentation](https://github.com/shadcn-ui/lint#readme) now documents React, Vue, and Svelte support, correcting the earlier secondary review: ESLint parses Vue and Svelte markup, while Oxlint sees only their script blocks. Upstream reports more than 150 agent task runs and near-universal correction within one round, but that is a first-party benchmark. Trigger: a Tailwind project has a named token or component-contract violation that Biome and framework checks miss; trial one violating and one valid fixture per enabled rule before adding the plugin. No Biome integration is documented.
- **[eslint-plugin-better-tailwindcss](https://github.com/schoero/eslint-plugin-better-tailwindcss)** — **EVALUATE CONDITIONALLY.** Upstream [Svelte parser documentation](https://github.com/schoero/eslint-plugin-better-tailwindcss/blob/main/docs/parsers/svelte.md) explicitly describes Svelte integration. Candidate for Tailwind class correctness; not evidence of component-contract enforcement equivalent to shadcn/lint. Requires ESLint plus the Svelte parser, which conflicts with the default desire for one broad Biome toolchain. Trial only when concrete missing rules justify that exception; verify Tailwind v4 behavior, dynamic classes, maintenance, license, and false positives before adoption.
- **[Stylelint](https://stylelint.io/)** — **WATCH for token/CSS policy gaps.** Candidate for restrictions on raw CSS values, properties, and custom conventions when Biome cannot enforce a named design-system rule. Check actual Svelte style-block parser support and rule packages before adding it. Avoid duplicating generic CSS lint already covered by Biome. No package installation or local trial performed.
- **[axe-core with Playwright](https://playwright.dev/docs/accessibility-testing)** — **USE THE EXISTING STACK PICK**, not a new watchlist dependency. Runtime accessibility checks complement Svelte compiler checks and token lint; they do not prove all accessibility or visual quality. Add checks to representative rendered pages plus explicit keyboard/focus tests. Keep visual snapshots for layout regressions separate from semantic accessibility assertions.

Evaluation protocol: seed one real violation and one valid example per promised rule; verify the selected linter parses the relevant framework markup rather than only script blocks; inspect actionable diagnostics and safe-fix behavior; record overlap and runtime cost. Do not trade framework semantic checking for a narrower design-system linter, or treat generated-design taste as objectively proved by static analysis.

### Agentic end-to-end testing

- **[TesterArmy e2e](https://tester.army/e2e.md)** — **TRIAL on one unstable user journey; do not replace Playwright.** This young Apache-2.0 TypeScript runner combines deterministic locators and assertions with model-driven `act`, `assert`, `waitFor`, and `extract` steps across web, iOS, and Android. Its sharpest mechanism is verified action caching: after a later check proves an agent action worked, continuous integration can replay the recorded controls without another model call and hand back to the agent only when the interface changed. Reports include cache outcomes, screenshots, traces, logs, and machine-readable results. Exploratory bug bashes require a deterministic failing reproduction before a finding counts.

  The boundary is sounder than agent-only browser testing because exact assertions remain code, but it is not deterministic end to end: semantic assertions still call a model, a replay can preserve a bad action if the later check is weak, and cache files execute with test authority. The project explicitly does not sandbox test code, tools, reporters, or app commands. Shared caches require code review, and untrusted pull requests need an external sandbox without secrets or write tokens. Trial against the existing Playwright path on one copy-sensitive or multi-step flow and compare authoring time, flake rate, model cost, cache handoffs, failure diagnosis, and defects caught. Keep stable and consequential assertions deterministic.

### Regeneratable components

Daniel Curtis argues that cheaper code generation weakens the case for maintaining every simple user-interface component in one shared package. The durable split is narrower: centralize the design system, tokens, accessibility rules, interaction contracts, and verification; regenerate low-risk layout and simple controls per project; keep difficult primitives such as comboboxes, date pickers, data grids, focus management, and keyboard behavior curated and shared.

This is a useful challenge to abstraction-by-default, not proof that shared libraries are obsolete. A configured audited primitive produces a smaller, safer diff than a fresh generated implementation. Regeneration earns trust only through token conformance, accessibility checks, interaction tests, visual regression, and pinned design inputs. Apply it when a shared package's upgrade and ownership burden is measured; do not use generation cost alone as the decision criterion.

Source: Daniel Curtis, [From Reusable to Regeneratable: Rethinking the Shared UI Component Library](https://www.infoq.com/articles/regeneratable-ui-component-library/), 2026-10-02.

### Third-party plan usage disclosure

OpenAI's [Sign in with ChatGPT UI/UX guidelines](https://developers.openai.com/siwc/ui-ux-guidelines) are not a general product-design standard. They are a good reference for delegated subscription or quota use: confirm the external plan on first connection, keep the current billing source visible near the model or composer, link directly to usage controls, distinguish third-party plan usage from the application's own charges, disclose eligible plans on pricing pages, and make quota recovery actionable. Generalize the transparency pattern, not OpenAI's branding or exact interface.

- **[AI interface design tools](design-tools.md)** -- Current design-first generators, editable canvases, code-aware bridges, app builders, free evaluation paths, hands-on aesthetic signals, and an anti-anchoring trial protocol. Magic Patterns is the current early aesthetic baseline; the next independent round should compare it with UX Pilot, Flowstep, Banani, and Superdesign. Re-check the dated landscape before a trial rather than copying its volatile pricing into this watchlist.
- **[SkillUI](https://github.com/amaancoderx/npxskillui)** -- **WATCH AS A PATTERN (reviewed 2026-09-12).** A small MIT command-line tool that statically extracts colors, typography, spacing, fonts, and component patterns from a URL or codebase, with an optional Playwright mode for screenshots, interaction states, animations, layout, and Document Object Model fingerprints; it packages the result as `DESIGN.md`, `SKILL.md`, `CLAUDE.md`, tokens, and visual references. The useful idea is converting observed design evidence into a reusable agent context package without model inference. Do not install on the strength of its 2.1k stars or demo: the repository has only seven commits, generated instructions are untrusted, website cloning raises provenance and design-rights questions, and its output is Claude-shaped rather than Workbench-portable. Revisit only to recover an owned project's design system or benchmark design extraction on an owned site, after source review and with generated instructions treated strictly as data.
- **[ArrowJS](https://github.com/standardagents/arrow-js)** -- **WATCH, unimpressed (reviewed 2026-09-12).** A tiny reactive DOM runtime whose meaningful distinction is a QuickJS/WebAssembly sandbox for executing generated component logic while trusted host code renders the DOM. The broader "UI framework for coding agents" pitch does not establish an advantage over mature frameworks, and the small ecosystem, tagged-template tooling, and remaining host-bridge and resource-limit threat model outweigh the core runtime's roughly 4.7 KB Brotli size. Do not replace an established frontend stack with it. Revisit only for a concrete requirement to render previously unknown, agent-generated interfaces at runtime, and then trial the sandbox rather than the general framework. Sources: [official site](https://arrow-js.com/) and [repository](https://github.com/standardagents/arrow-js).
- **[Blume](https://github.com/haydenbleasel/blume)** -- **WATCH (reviewed 2026-09-12).** An MIT-licensed, Markdown-first documentation framework built on Astro and Vite. Its useful bundle is content-only ownership plus static HTML, local search, raw Markdown URLs, `llms.txt`, a JSON API, and optional Model Context Protocol access; `blume eject` provides an escape into a standalone Astro project. This is more coherent than adding AI discoverability to a conventional docs template piecemeal, but it is a new single-maintainer project and Workbench does not currently need a published documentation application. Evaluate when a public project needs a real docs site for both people and agents; compare against Astro Starlight and verify generated-project transparency, upgrade behavior, accessibility, search quality, dependency footprint, and the security boundary of optional AI features. Sources: [official documentation](https://useblume.dev/docs) and [repository](https://github.com/haydenbleasel/blume).
- **[Zero (Rocicorp)](https://zero.rocicorp.dev/)** -- General-purpose sync engine for local-first apps. Instant local reads + server reconciliation; optimistic mutations with built-in conflict resolution. Pitch: "absurdly fast" UI because data is already on-device. Worth evaluating for any product where perceived latency dominates (especially LLM-backed UIs where the model call is slow). See Scott Tolinski's video ([YouTube](https://www.youtube.com/watch?v=aV6aM3R74AQ)) for the practitioner take.
- **[Storybook](https://storybook.js.org/)** -- Component workshop / dev environment for UI components in isolation. The de facto standard for design-system documentation, visual regression testing, and component-level interaction testing. Its preview [MCP server](https://storybook.js.org/docs/ai) exposes generated component and documentation manifests, live stories, story generation, and component tests to coding agents. That is the useful agent-ready pattern: give the model a maintained semantic map plus executable examples, not screenshots alone. The AI surface is currently React-only and preview quality. Evaluate when component count crosses ~30 and review-by-screenshot becomes a bottleneck. Pairs naturally with Chromatic for visual diffing.
- **[Framer Motion](https://www.framer.com/motion/)** -- React animation library with a declarative API (`motion.div` + `animate` / `initial` / `exit` props). The mainstream choice for "we need animations beyond CSS transitions but don't want to wire up GSAP." Strong gesture support (drag, pan, hover) and layout animations. Evaluate for any UI where motion telegraphs state changes (loading, success, list reorder).
- **[Base UI](https://base-ui.com/)** -- Unstyled, accessible React component primitives from the team behind Radix UI and Material UI. Headless: you bring the styles. Successor / sibling to Radix Primitives. Evaluate when building a custom design system and want correctness (a11y, keyboard, focus management) without inheriting visual opinion. Likely default over Radix for new projects in 2026.
- **[TanStack](https://tanstack.com)** -- Type-safe data fetching, routing, forms. Evaluate for replacing ad-hoc React data layer.
- **[Vite+](https://voidzero.dev/posts/announcing-vite-plus-1-0)** -- Stable 1.0 unified Node/Vite toolchain. Watch-only after the local comparison; the [runtime exploration](../languages/typescript/runtimes.md) owns the comparison. Adopt only if it removes overlapping configuration while preserving framework checks.
- **[Vite Task](https://viteplus.dev/guide/run)** -- Interesting automatic input tracking, caching, and dependency ordering, currently coupled to the Vite+ control plane. Watch until a real monorepo need exceeds Just.
- **[Oxfmt](https://oxc.rs/blog/2026-02-24-oxfmt-beta)** -- Fast Prettier-compatible formatter on watch for framework coverage. Keep adequate Biome coverage; evaluate Oxfmt with the [Vite+ comparison](../languages/typescript/runtimes.md).
- **[Leptos](https://leptos.dev)** -- Rust full-stack web framework. Evaluate for Rust-heavy teams.
- **[Dioxus](https://dioxuslabs.com/)** -- Rust full-stack crossplatform app framework (web, desktop, mobile). Alternative to Leptos; evaluate when a single Rust codebase needs to ship to multiple platforms.
- **Enhance** -- Backend-first web framework. Read: [How To Build an App With Enhance](https://thenewstack.io/how-to-build-an-app-with-enhance-a-backend-first-framework/).
- **[Astryx](https://astryx.atmeta.com/)** (Meta, beta 2026) -- OSS design system: React + StyleX, 160+ accessible themeable components, dark mode, CLI scaffolding + theme generation. Grown internally at Meta for 8 years; claims 13k+ apps. The notable part for us: **"agent ready" is a first-class pitch** -- agent-oriented docs plus an MCP server, i.e. a design system built to be *consumed by coding agents*, not just humans. Tension: React-coupled, so per our classifier it's a skip for the Svelte stack -- evaluate for any React surface, and **study it as the reference pattern for agent-ready component docs/MCP regardless of framework**.

### Cross-platform desktop applications

- **[Tauri](https://v2.tauri.app/start/)** remains the default when a web frontend needs native desktop distribution. It reuses the operating-system webview, has the strongest fit with the existing Svelte and Rust guidance, and already has an owned stack page. Better Stack's [Tauri, Electrobun, and Deno Desktop comparison](https://www.youtube.com/watch?v=ktkDGQyRx3Y) was a useful survey, but did not expose a current desktop-app need or displace Tauri.
- **[Wails](https://wails.io/docs/introduction/)** is the equivalent Go-shaped choice: system webviews, Go methods exposed to JavaScript, generated TypeScript models, and Svelte templates. Better Stack's [screen-recorder comparison](https://www.youtube.com/watch?v=Q1TL2AKoy00) found it credible but showed the practical ecosystem boundary: native platform APIs may require custom Cgo and Objective-C when the Go package ecosystem has no wrapper. Use Wails when Go is already the application's center of gravity; do not introduce Go merely to avoid Rust in Tauri.
- **Electrobun** remains watch-only when a desktop product needs it.
- **Deno Desktop (reviewed 2026-10-14)** remains excluded by the [runtime maintenance decision](../languages/typescript/runtimes.md#why-denos-outlook-changes-the-choice); Tauri remains the default. The official [comparison](https://docs.deno.com/runtime/desktop/comparison/) describes `deno desktop` from Deno 2.9, with system WebView or bundled Chromium Embedded Framework (CEF), framework detection, cross-compilation, and binary-diff updates. Its useful proposition is a TypeScript backend without adding Rust, with optional consistent rendering; the size and compatibility comparisons are vendor claims, not local measurements. The same page lists missing Windows auto-update, native secure storage, and desktop runtime permission prompts, plus separate macOS notarization. Do not infer desktop containment from Deno's general permission model or confuse cross-compilation with signed distribution. Revisit only for a concrete desktop application after a credible maintenance commitment beyond the announced runtime horizon; then verify Svelte integration, native dependencies, signed installation and updates on each target OS, rendering, and the frontend-to-backend authority boundary. No desktop build or packaging trial was performed.
